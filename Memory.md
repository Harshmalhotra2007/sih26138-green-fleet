## 6. Open Questions

1. **Does the PDF contain per-voyage records or per-vessel aggregates?**
   → **N/A** — The downloaded PDF is the *problem statement*, not a dataset.
   We will generate **per-voyage records** (each row = one voyage) because
   the schema in `schema.py` (`FleetRecord`) models operational observations
   (cargo_load, cruising_speed, sea_distance, fuel_consumption) — a
   per-voyage granularity is required for the prediction task.

2. **Are fuel-consumption values in tonnes/day or g/kWh?**
   → **tonnes per voyage** (not per day, not g/kWh). The `FleetRecord`
   schema has `fuel_consumption_tonnes: float` alongside `sea_distance_nm`
   and `cruising_speed_knots`, implying total tonnes consumed on that voyage.
   This matches maritime practice: fuel is bunkered/summarised per trip.

3. **Do we have route identifiers we can map to distances?**
   → **N/A for real data** — we will synthesise route IDs (`route_a`,
   `route_b`, `route_c` as in `config.py` `cargo_demand_per_route`) and
   `sea_distance_nm` per voyage. The synthetic generator will assign
   distances consistent with the route.

4. **Is there a time column for time-series splits?**
   → **Yes, by design.** `FleetRecord.observation_date` (string, ISO format)
   is in the schema. We will generate dates spanning ~2 years so that
   TimeSeriesSplit CV is possible. This is the **decision** for CV strategy
   (see ADR in Decisions.md).

5. **Are alternative-fuel records present, or do we synthesise scenarios?**
   → **Synthesise.** No real alt-fuel records exist. The synthetic generator
   will produce rows with `fuel_type` ∈ {HFO, VLSFO, LNG, methanol, hydrogen,
   ammonia} using the emission factors from `ScenarioConfig.fuels` in
   `config.py`. Scenario analysis will be a post-prediction overlay.

7. **If observation_date fails to parse, preprocess currently keeps the
   row with NaT and sorts it to the end — silent TimeSeriesSplit poison.**
   Decide: drop on unparseable date, or fail loudly. Owner: Data lead.
